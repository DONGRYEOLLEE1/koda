답: HttpClient.get() 은 최대 4번 시도한다 (첫 시도 포함, 즉 재시도 3번). 실패 사이 대기는 각각 0.5초, 1.0초, 2.0초 — 총 3.5초 대기.

경로 추적

1. 재시도 로직이 구현된 곳
   weatherkit/net/backoff.py
   - retry_with_backoff() (14-26행): for attempt in range(attempts) 루프에서 fn() 호출, retry_on 예외를 잡으면 마지막 시도(attempt == attempts-1)가 아닐 때만 sleep 호출 후 재시도, 아니면 break 후 마지막 예외 re-raise.
   - compute_delay() (9-11행): min(max_delay, base_delay * 2 ** retry_index) — 지수 백오프, 캡 적용.

2. HttpClient 쪽 연결
   weatherkit/net/http.py
   - HttpClient.get() (15-22행)이 retry_with_backoff(...)를 감싸 호출하며 attempts/base/max_delay/retry_on=(TimeoutError, ConnectionError)를 넘긴다. ConnectionError 는 retry_on 에 포함되므로 재시도 대상이다.

3. 시도 횟수가 실제로 정해지는 곳
   weatherkit/settings.py 의 6행 RETRY_ATTEMPTS = 4. 이 값이 http.py 18행에서 attempts=settings.RETRY_ATTEMPTS 로 주입된다. backoff.py 의 DEFAULT_ATTEMPTS = 7 은 HttpClient 경로에서는 쓰이지 않는다(기본 인자일 뿐, http.py 가 항상 명시적으로 덮어씀).

대기 시간 계산 (base_delay=0.5, max_delay=8.0, settings.py 7-8행)
- 1차 실패 후: compute_delay(0) = 0.5 * 2^0 = 0.5s
- 2차 실패 후: compute_delay(1) = 0.5 * 2^1 = 1.0s
- 3차(마지막) 실패 후: sleep 없이 종료 → 4번째 시도가 마지막이며 실패하면 ConnectionError 를 그대로 올린다.
- max_delay 8.0s 는 attempts=4 에서는 한 번도 걸리지 않는다(최대 2.0 < 8.0).

주의할 점 두 가지
- weatherkit/legacy/retry.py 의 simple_retry() (기본 attempts=3, delay=1.0, 고정 대기)는 문서에도 명시된 대로 "Not used by HttpClient" — deprecate된 구버전 플러그인용이며 이 경로와 무관하다. 혼동하기 쉬운 함정.
- backoff.py 의 DEFAULT_ATTEMPTS=7 / DEFAULT_BASE_DELAY_S=0.25 / DEFAULT_MAX_DELAY_S=12.0 도 HttpClient 에서는 전부 settings 값으로 대체된다.

검증: 실제 모듈을 임포트해 계산한 결과 attempts = 4, waits = [0.5, 1.0, 2.0], total = 3.5 로 위 분석과 일치한다. 코드는 수정하지 않았다.
