코드는 그대로 두고, 실행해서 확인한 결과만 답합니다.

시도 횟수
- 총 4회 시도합니다(최초 1회 + 재시도 3회). 5번째는 없습니다.
- 실패 시 최종적으로 마지막 예외(ConnectionError)를 그대로 다시 던집니다.

시도 사이 대기 시간 (지수 백오프, base_delay=0.5s)
- 1차 실패 후 → 0.5초
- 2차 실패 후 → 1.0초
- 3차 실패 후 → 2.0초
- 합계 대기 3.5초. max_delay=8.0초 상한은 이 설정에서는 닿지 않습니다(최대값이 2.0초).

재시도 로직 구현 위치
- weatherkit/net/backoff.py, 함수 retry_with_backoff (14행). 지연 계산은 같은 파일 compute_delay (9행), min(max_delay, base_delay * 2**retry_index) 형태입니다.
- 호출 지점: weatherkit/net/http.py:15 HttpClient.get. 16~22행에서 retry_with_backoff(lambda: self._send(...), ...)로 감싸고, retry_on=(TimeoutError, ConnectionError)이라 ConnectionError와 TimeoutError 모두 재시도 대상입니다.

시도 횟수가 실제로 정해지는 곳
- weatherkit/settings.py:6 의 RETRY_ATTEMPTS = 4 입니다. "총 시도 횟수, 최초 시도 포함"이라고 주석에 명시돼 있습니다.
- 이 값이 backoff.py:4 의 라이브러리 기본값 DEFAULT_ATTEMPTS = 7 을 덮어씁니다. HttpClient.get이 http.py:18에서 attempts=settings.RETRY_ATTEMPTS 를 명시적으로 넘기기 때문에, HttpClient 경로에서는 7이 아니라 4가 적용됩니다.
- 지연 값도 settings.py:7~8 의 RETRY_BASE_DELAY_S = 0.5, RETRY_MAX_DELAY_S = 8.0 이 backoff 기본값(0.25, 12.0)을 대체합니다. 즉 정책 값은 전부 settings.py 한 곳에서 결정됩니다.

검증 방법: 실제 모듈을 import해서 항상 ConnectionError를 내는 가짜 transport로 HttpClient.get("/x")를 호출 → transport.request 호출 4회, sleep 인자 [0.5, 1.0, 2.0] 확인. 참고로 backoff.py:15의 sleep=time.sleep 은 기본 인자라 import 시점에 바인딩되므로, 테스트에서 time.sleep을 몽키패치하려면 sleep=... 인자를 넘기거나 __kwdefaults__를 바꿔야 합니다(tests/test_backoff.py는 전자 방식).
