코드 수정 없이 읽기만 했습니다. 답변은 다음과 같습니다.

시도 횟수: 총 4회 (첫 시도 포함, 즉 추가 재시도 3회)
`RETRY_ATTEMPTS = 4` 가 "total attempts per request, first try included" 로 정의되어 있어서, ConnectionError가 계속 나도 4번째 시도에서 포기하고 마지막 예외를 그대로 올립니다(raise last_exc). 5번째 시도는 없습니다.

시도 사이 대기 시간: 0.5초 → 1.0초 → 2.0초 (총 3회 대기, 합계 3.5초)
지수 백오프 `min(max_delay, base_delay * 2**retry_index)` 에 base=0.5, max=8.0 이 적용된 결과입니다.
- 1번째 재시도 전: 0.5 * 2^0 = 0.5초
- 2번째 재시도 전: 0.5 * 2^1 = 1.0초
- 3번째 재시도 전: 0.5 * 2^2 = 2.0초
- 마지막(4번째) 시도 실패 시에는 대기 없이 바로 예외를 던집니다.
max_delay=8.0 은 시도 횟수가 4회뿐이라 실제로 걸리는 일이 없습니다.

재시도 로직이 있는 파일/함수
- 재시도 루프 본체: weatherkit/net/backoff.py — `retry_with_backoff(fn, *, attempts, base_delay, max_delay, retry_on, sleep)`, 그리고 지연 계산은 같은 파일 `compute_delay()`.
- 이를 호출하는 곳: weatherkit/net/http.py:15 — `HttpClient.get()`. `_send()`로 transport.request("GET", ...)를 감싸고, `retry_on=(TimeoutError, ConnectionError)` 로 두 예외만 재시도 대상으로 잡습니다.
- 참고: weatherkit/legacy/retry.py 의 `simple_retry()` 는 "Not used by HttpClient" 라고 명시된 폐기된 헬퍼로, 이 경로와 무관합니다(attempts=3, delay 고정 1.0초).

시도 횟수가 실제로 정해지는 위치
값의 출처는 weatherkit/settings.py:6 의 `RETRY_ATTEMPTS = 4` 이고, 소비 지점은 weatherkit/net/http.py:18 의 `attempts=settings.RETRY_ATTEMPTS` 입니다. 즉 숫자는 settings에서 정해지고, 루프는 backoff.py:18 `for attempt in range(attempts)` 가 그 값을 그대로 사용합니다.

주의할 점: backoff.py:4 의 `DEFAULT_ATTEMPTS = 7`, `DEFAULT_BASE_DELAY_S = 0.25`, `DEFAULT_MAX_DELAY_S = 12.0` 은 라이브러리 기본값일 뿐이고, HttpClient는 세 값 모두 settings 값(4 / 0.5 / 8.0)으로 덮어써서 호출합니다. 따라서 backoff.py 기본값(7회, 0.25초 시작)을 보고 판단하면 오답입니다. backoff.py를 직접 호출하는 tests/test_backoff.py 도 HttpClient의 실제 정책과는 별개입니다.

한 가지 덧붙이면, weatherkit/cache.py 의 TTLCache(300초) 때문에 같은 도시를 반복 조회하는 경우에는 재시도 자체가 일어나지 않을 수 있습니다(캐시 히트 시 `client.get` 미호출).
